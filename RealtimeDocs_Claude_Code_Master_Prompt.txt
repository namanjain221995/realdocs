9. DURABILITY, OFFLINE RECOVERY, AND HISTORY

Connected, synchronized, and durably saved are different states. Show Saved only after a server acknowledgment establishes that the corresponding pending changes have committed to persistent storage.

Implement ordered persistence per document with monotonic revisions or an equivalent durable update log. Prevent older asynchronous writes from overwriting newer state. Any compaction must retain updates beyond its committed boundary.

The acknowledgment scheme must cover all pending changes, including deletion-only operations. State-vector equality alone is not sufficient evidence for every kind of saved change. Test the chosen design directly.

A database error must never produce a false Saved indicator. Keep pending work recoverable, surface the error, and recover when the database returns. Graceful shutdown helps but is not a substitute for crash-safe acknowledged persistence.

For signed-in editors, provide scoped local pending-change recovery using an appropriate local store. Partition it by account, document, and generation; clear it appropriately on logout. Guest viewers should not persist confidential documents locally by default.

On reconnect, reauthorize before accepting offline changes. If editing access was removed, preserve a clearly separated recoverable local draft where appropriate without publishing it. Do not promise remote wiping of previously received data.

Snapshot restoration must establish a new document generation or another tested boundary so stale offline updates cannot silently resurrect content from the abandoned generation.
