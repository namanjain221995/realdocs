# Testing

For the engineer who maintains the tests. It lists every suite and how to run it, maps the 20
required acceptance scenarios to the tests that cover them, records what was observed when the
suites were run (2026-11-11, this host: Ubuntu 24.04, aarch64, Docker, no display), and says what is
**not** tested.

Rules used in this document:

- "Covered" means a test exercises the real component whose correctness is claimed (real server,
  real PostgreSQL, real browser engine, real Electron), not a mock of it.
- A test is named here only if its file was read. Counts are those observed in the runs listed in
  section 4.
- Every command needs the pinned toolchain first: `. scripts/dev-env.sh;` (Node 24.22.2, pnpm 12.18.0).
  The root `.env` is never created by any test.

### 1.1 The acceptance suite (`tests/e2e`, package `@realtimedocs/e2e`)

```
tests/e2e/stack.mjs        PostgreSQL (rd-e2e-pg) + the real server bundle serving the real web build
                           (built into tests/e2e/.stage/web, so apps/web/dist is not touched), first
                           administrator, sample document, and a control endpoint (stop / kill / start the
                           server, stop / start PostgreSQL, restart with COLLAB_TICKET_TTL_SECONDS)
tests/e2e/run.mjs          starts the stack, runs the specs in the Playwright image, stops everything
tests/e2e/playwright.config.ts   projects chromium, firefox, webkit and disruptive-<browser>
tests/e2e/support/test.ts  helpers (sign-in, API from the page, paste, export, control calls)
tests/e2e/specs/*.spec.ts  the specs (section 3)
tests/e2e/fresh-setup/     scenario 20: README steps in an isolated Compose project
```

- `pnpm test:e2e` runs the normal projects first (three workers), then the `disruptive-*` projects
  (`restart`, `db-outage`, `ticket-renewal`) with one worker, because they stop or kill the shared
  server or database. Never run those next to other specs. Arguments after `--` replace the default
  projects: `pnpm test:e2e -- --project=chromium -g images`. `--no-build` reuses
  `tests/e2e/.stage/web`; `--keep-stack` leaves the stack up (stop it with `node tests/e2e/stack.mjs down`).
- `apps/web/test-real/stack.mjs` could not be reused: its ports, container and state file are compiled
  in, and its helper module reads the state file at import time. The shape of the new stack is the same.
- The server rate limits per client address (sign-in, share exchange, invitations, upgrades, tickets)
  are raised for this stack because one address plays every user. Per-account, per-link and per-socket
  limits are the defaults.
- Pictures and traces of failures are in `tests/e2e/.stage/test-results/` (ignored by git).
- `E2E_SHOW_KNOWN_DEFECTS=1` used to run the simultaneous-Enter test as an ordinary test while it was a known defect. That defect was fixed on 2026-11-12, the test is now an ordinary test, and the variable is no longer used (section 5.1).

## 5. Defects and failures found

### 5.1 Simultaneous paragraph splits put text in the wrong paragraph (product defect, fixed on 2026-11-12)

Observed in Chromium, Firefox and WebKit. Two or three editors press Enter at the same instant in one
document (same place, and, intermittently, also in adjacent paragraphs). The clients still converge on
one document and the server stores it, but it is not what was typed: empty paragraphs appear, text of
two lines is merged ("Y444ZX"), the first character of a line lands in another editor's line, and in
one run a character was duplicated. Typing alone (no splits), one editor splitting while others type,
and splits taken in turns all behave. Reproduction: `E2E_SHOW_KNOWN_DEFECTS=1 pnpm test:e2e -- --project=chromium -g "same instant"`
(`specs/convergence.spec.ts`, "known product defect"); the test opens three editors on one document and, six
rounds in a row, has all three press Enter and type a short token at the end of the document at the same
time. Expected: 18 paragraphs equal to the tokens; observed: empty paragraphs and mixed tokens. The
mechanism was not investigated (the editor binds ProseMirror to Yjs through `@tiptap/y-tiptap`).
Without the environment variable the test was marked `test.fail`, so the suite stayed green and would turn
red when the defect was fixed.

**Resolution (2026-11-12).** The cause was found. After a remote change, `@tiptap/y-tiptap` 3.2.0
re-places a caret that sits at the start of a text block by guessing "the n-th block with this type and
text". When another editor had just added an identical block (an empty paragraph) before it, the caret
moved into the other person's paragraph and the next keystrokes landed there. The shared Yjs document
was always correct: there was no lost or duplicated content at the CRDT level, no schema corruption and
no divergence; only characters typed at that moment went to the wrong paragraph. The fix is the
`CaretKeeper` plugin in `packages/editor/src/editor/collabPlugins.ts`, which keeps the exact Yjs relative
position when the block it points into still exists. It is covered by
`packages/editor/test/concurrent-enter.test.ts` (4 tests). The `test.fail` mark and the
`E2E_SHOW_KNOWN_DEFECTS` variable were removed, so "simultaneous Enter" in
`tests/e2e/specs/convergence.spec.ts` is a normal test; it passed in Chromium, Firefox and WebKit (9/9
with `--repeat-each=3`, and in the full acceptance suite). The description above is kept as the history
of the defect.

### 5.2 Editor browser check `callout-toolbar` in WebKit: two test races, fixed

- "inactive again: expected "false", got "true"": the toolbar recomputes its state on the next animation
  frame after a transaction (`useToolbarState`), and the check read `aria-pressed` once, right after waiting
  on the other pane. The three `aria-pressed` reads now wait up to 3 s for the expected value; the
  assertions themselves are unchanged. Product behaviour is correct one frame later.
- "the callout control is reachable with the arrow keys of the toolbar" (seen once while confirming the
  first fix): WebKit can take `Alt+F10` before it routes keys to the just-focused editor, so the arrows
  moved the text cursor. The check now waits until focus is inside the toolbar (one more `Alt+F10` at most)
  and asserts that before walking the toolbar.
- After both fixes (lead, 2026-11-11): `callout-toolbar` alone 5 of 5 passed in WebKit; full runs Chromium
  38/38, Firefox 36/36 (2 skipped), WebKit 36/36 (2 skipped).

### 5.3 Observation: the CSP does visible work while the clipboard sanitiser parses

With the real CSP, pasting the hostile corpus makes the browser report 18 refused inline handlers and a
refused `<base href>` (`script-src-attr`, `base-uri`). Nothing executes and the spec asserts only these
expected reports. The same corpus is verified with no CSP at all only in the editor's own browser
check `malicious-corpus-without-csp`; the end-to-end spec relies on the policy being present.

## 6. What is not tested

- **Native Windows and macOS.** Since 2026-11-12 CI has started the packaged app on Windows x64, macOS arm64 and macOS x64 (`apps/desktop/scripts/launch-check.mjs`: it stayed running for 20 seconds), but nobody has operated it by hand there; window compositing,
  `setContentProtection` (capture exclusion), click-through hover recovery, tray and menu bar, Spaces,
  fullscreen, Retina, OS key stores, installers, signing and notarisation are not exercised
  (`docs/notes/desktop.md` §7.4 and §9 list the manual checklist).
- **Real meeting capture** (Zoom, Teams, Meet, OBS): no test shares a screen with a real tool.
- **Real Safari** (macOS, iOS), **real phones and tablets**, touch input: Playwright's Linux WebKit
  and viewport emulation are not those.
- **Screen readers** and other assistive technology: axe finds only rule-based problems.
- **HTTPS**, `Secure` cookies, `wss://`, a reverse proxy in front of the server: the stacks use HTTP on loopback
  (the server has proxy tests in `proxy.test.ts`, run in the integration suite).
- Real clipboards of Google Docs, Word, Excel (fixtures only), real IME input outside Chromium's simulation.
- Long real-time expiry of account sessions through the browser, rate limits through the interface,
  documents near the size limits, many (more than three) simultaneous editors, performance
  (`tests/perf`, a separate agent).
- Windows and macOS builds and `test:packaged` were not run by the author of this document. The release workflow later built them on GitHub's native runners (run 43195585865) and ran the launch check; Windows arm64 and Linux arm64 were never started on their own architecture in CI.
- The `deploy/` installation itself. Multi-instance servers and the upgrade of a populated database were exercised on this host in throw-away resources ([scaling.md](scaling.md), [upgrade-and-rollback.md](upgrade-and-rollback.md)); the upgrade was later applied to the live deployment on 2026-11-12 and checked with `scripts/live-smoke.mjs` (26/26 checks); the multi-instance setup was not run on the live deployment.

### 6.1 The Linux Electron/Xvfb tests are Linux smoke tests only

Scenario 18 and the desktop smoke and real-stack suites run the Linux build of Electron under Xvfb,
without a window manager, compositor, tray host or display capture. Xvfb has no compositor, and
`setContentProtection` is not implemented on Linux. A passing run shows that the app starts, that its
main process, preload, IPC rules, CSP, network policy and the connection to the real server work in
that environment. It is **not** evidence for the product's Windows and macOS behaviour (transparency
over other windows, capture exclusion, click-through, shortcuts, tray). Linux is not a product target.
Do not cite these results for any native claim.
